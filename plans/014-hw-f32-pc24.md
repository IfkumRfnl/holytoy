# Plan 014: Hardware F32 semantics via x87 precision control (PC24)

Status: DONE (2026-07-17, branch plan-014-hwf32; see "## Implementation
findings" for completion evidence: 14/14 proofs incl. HT PC24 OK, corpus
visual 32/39 zero regressions, Greek Temple 734 -> 165 ms/frame). Depends on plan
013 (F32 semantics; this plan removes its per-op software-rounding cost
without changing its semantics). Motivated by a real heavyweight workload:
iq's "Greek Temple" (Shadertoy ldScDh, adapted to single-pass/texture-free
for local testing only — its license forbids committing the shader; the
adaptation lives outside the repo) compiles and renders **visually correct**
(96.2%/95.9% within 16/255 vs llvmpipe, both states) but takes **734 ms per
frame at 1:16 on 4 cores under KVM** — the adaptive controller's coarsest
scale, ~0.6 ms per shaded sample.

## Why it is slow (measured, run-20260717-192848-C3KLNQ and -193314-v2Niym)

Plan 013 wraps **every scalar float op** in `HtF32(...)` — a non-inlined
call chain `HtF32 -> HtF32BitsRNE -> HtF32FromBits` (~50 lines of integer
bit-twiddling) — and **every float literal** in a runtime `HtF32(lit)`
re-rounded on every evaluation. Microbench (n=2M, KVM):

| variant                                | net ns/op | note |
|----------------------------------------|-----------|------|
| native F64 mul (loop baseline subtracted) | 2.4    | |
| `HtF32(x*y)` call chain (shipped)       | 13.3      | the plan-013 tax |
| flattened single-call HtF32             | 6.7       | |
| inline Veltkamp split                   | 2.4       | **wrong in-guest**: HolyC keeps 80-bit x87 intermediates (verified: `(1+2^-60)-1 != 0`), so the split theorem does not hold |
| native F64 mul with CW.PC=24            | 2.4       | **bit-exact vs HtF32** |

The decisive facts (probe `BENCHPC.HC`, run-20260717-193353-cak36L):

1. TempleOS runs the x87 at CW `0x037F` = 64-bit significand; HolyC keeps
   intermediates in registers, so software rounding tricks need calls.
2. With CW precision control set to 24-bit (`0x007F`), native
   `FMUL/FADD/FDIV` results are **bit-identical to `HtF32`** on 200k
   values x 3 ops including 66k exact RNE-tie patterns (mul=0 add=0 div=0
   mismatches), at **zero cost over native F64** (5 ms vs 5 ms per 2M ops;
   the HtF32 chain costs 33 ms).
3. The FPU control word is **task-local**: Sched.HC FXSAVE/FXRSTORs
   `CTask.fpu_mmx` on every switch, so shade tasks can hold PC24 without
   affecting any other task.
4. A CW save+set+restore round trip costs ~11 ns — negligible when hidden
   behind a transcendental call, unmeasurable per frame.

## Design

Generated shader code is three-address: every float op already lands in
its own statement/temp. Under PC24 each x87 arithmetic instruction rounds
its result to a 24-bit significand (RNE) in-register, so **emitting plain
ops under PC24 reproduces plan 013's per-op F32 rounding bit-for-bit** for
`+ - *` (exact-in-F64 then one rounding, identical by construction) and
makes `/`, `sqrt` *single-rounded* — exactly what llvmpipe's `fdiv`/
`sqrtss` do (plan 013's software path double-rounds those through F64;
documented there as a ~1/2^29 1-ULP artifact, which this plan removes).

Known semantic edge vs llvmpipe (documented, corpus-measured): PC24 rounds
the significand only; the **exponent range stays extended**, so F32
overflow (->inf) and underflow (->subnormal/zero) do not occur at the F32
boundary. Shader math that leaves [2^-126, 2^128) diverges from llvmpipe
there. The software path handled those exactly; corpus stratum A never
exercises them (verified by the zero-regression gate below).

Mechanics:

- **`MainImage` glue sets PC24** on entry and restores on exit — the one
  choke point through which the SMP workers, exec probes, and visual dumps
  all call the shader. `HtShaderInit` (install-time global initializers)
  wraps itself the same way.
- **Emitter hw mode** (`e->hw`, default ON, product of `ht_f32_mode` and a
  new `ht_hwf32_mode`): float binary/compound ops emit plain
  `d=(x)op(y);`; literals emit `ht_glit[k]` references backed by a table
  filled once inside `HtShaderInit` via `ht_glit[k]=HtF32(<text>);`
  (dedup by text; overflow past HT_GLIT_MAX falls back to the runtime
  call). Int->float conversions keep the `HtF32` call (rare, correct).
- **Builtin routing under hw**: `sqrt`->`Sqrt` (FSQRT@PC24 = sqrtss),
  `inversesqrt`->`HtInvSqrtHf` (1.0/Sqrt), `fract`->`HtFractHf`,
  `mod`->`HtModHf`, `mix`->`HtMixHf`, and Hf twins of the plan-013
  cross-component helpers (dot/len/dist/norm/cross/reflect/mat*) — same
  formulas, no `HtF32` wrappers, relying on caller PC24.
- **`HtSinCosF32` forces PC64 internally** (save CW / set / restore): its
  Cephes replica needs exact F64 products for the fma reproduction. Same
  for the non-replicated kernel transcendentals under hw mode
  (`HtExpHf/HtLnHf/HtLog2Hf/HtExp2Hf/HtPowHf/HtTanHf/HtASinHf/HtACosHf/
  HtAtanHf/HtAtan2Hf/HtSStepHf`) so their numerics stay bit-identical to
  the sw mode (conservative: hw mode must not change plan-013 semantics
  through the back door).
- **Self-test gate** `HT PC24 OK` in `HtLibSelfTest`: under PC24, native
  mul/add/div must bit-match `HtF32` on the recorded patterns + tie
  sweeps, and `(1+2^-60)-1` must flush to 0. On failure (e.g. an emulator
  that ignores PC) print `HT PC24 SWFALLBACK` and clear `ht_hwf32_mode`
  before any compile — the plan-013 software path remains fully intact as
  the fallback.
- **Escape hatch**: `HOLYTOY_HWF32=0` -> `E:/HWF32.TXT` (mirrors F32.TXT)
  for A/B measurement.

## Implementation findings (2026-07-17)

- **HolyC inline-asm gotcha (cost one debug cycle):** plain locals are
  register-allocated, so `asm {FSTCW U16 &cw[RBP]}` writes a stack slot the
  compiled code never reads — and the subsequent FLDCW loaded garbage,
  unmasking x87 exceptions (#MF storm in the generated `HtShaderInit`).
  The scratch locals must be declared `I64 noreg cw;`
  (`Demo/Asm/AsmAndC1.HC` documents the convention). Probe
  `run-20260717-195503-LuAQRz`: read 037F, PC24 007F, `(1+2^-30)-1==0`,
  restore 037F.
- **Greek Temple (motivating workload), 640x480 at 1:16, KVM, 4 cores:**
  734-763 ms/frame with plan-013 software rounding -> **165 ms/frame with
  PC24 hw mode (4.5-4.6x)**; generated HolyC 97,516 -> 96,506 bytes,
  in-guest compile 78 -> 41 ms. Visual dumps **byte-identical to the
  sw path** on both pinned states (V00A/V00B, 8640 bytes each), score vs
  llvmpipe unchanged (96.2%/95.9% within 16/255).
- `HOLYTOY_HWF32=0` A/B verified: prints `HT HWF32 MODE OFF`, restores the
  software path and its timing.
- **Corpus v2 (hw mode default ON):** compile/install/exec 39/39 stratum A,
  0/12 stratum B (texture diagnostics, unchanged); **visual 32/39 — zero
  regressions**, per-shader mean/max/pct match the plan-013 completion
  table (e.g. XdsGWH 25.5/25.5 identical both modes; 4sfGWX 97.8/99.6).
  The 7 FAILs are the same chaotic-raymarcher set, scores unchanged.
- **Proofs: 14/14 green** with hw mode default-ON, including the new
  `HT PC24 OK` gate (holytoy proof), the oracle proof (gradient dump
  100.0/100.0 exact vs committed refs — bit-stable), the editor proof
  (frame hash `6d5c42e03ecb...` unchanged from plan 010), and the SMP
  proof (CORES=1 == CORES=4 identical viewport hash).
